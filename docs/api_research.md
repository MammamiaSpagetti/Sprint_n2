# Исследование API «Доски»

Дата: 27 сентября 2026 года.

## Источник и способ проверки

Адрес приложения: https://qa-desk.education-services.ru/.
В браузере проверены формы регистрации и создания объявления; через интерфейс
созданы временный пользователь и временное объявление.

Адреса API, HTTP-методы, заголовки и построение тела запроса извлечены из
JavaScript-файла, который загружает сам фронтенд:
https://qa-desk.education-services.ru/static/js/main.672da7a6.js.
В нём функции регистрации и входа отправляют JSON через `fetch`, а создание
и изменение объявления используют `FormData` и Axios.

Запросы воспроизведены API-клиентом на `requests`; приведённые ниже статусы,
структуры и сообщения получены от работающего сервера. Готовые решения и
сторонняя документация API не использовались. HAR из Chrome не записывался;
ниже отдельно приведены шаги для самостоятельной проверки через DevTools.

Базовый адрес: `https://qa-desk.education-services.ru/api`.
Защищённые запросы используют `Authorization: Bearer <access_token>`.
В примерах email, ID, даты и токены заменены обозначениями;
HTTP-статусы и тексты ошибок сохранены.

## Регистрация

`POST /signup`, `Content-Type: application/json`.

```json
{
  "email": "sprint2_<uuid>@example.com",
  "password": "Sprint2_Test_2026!"
}
```

Успех: **201 Created**.

```json
{
  "user": {
    "id": 123,
    "name": "User",
    "email": "sprint2_<uuid>@example.com"
  },
  "access_token": {
    "access_token": "<token>"
  }
}
```

Повторная отправка с тем же email: **400 Bad Request**.

```json
{
  "statusCode": 400,
  "message": "Почта уже используется"
}
```

Поле подтверждения пароля существует в форме для клиентской проверки;
в API передаются `email` и `password`.

## Авторизация

`POST /signin`, `Content-Type: application/json`.
Тело содержит `email` и `password` зарегистрированного пользователя.

Успех: **201 Created**.

```json
{
  "user": {
    "id": 123,
    "name": "User",
    "email": "sprint2_<uuid>@example.com",
    "avatar": null,
    "admin": false
  },
  "token": {
    "access_token": "<token>"
  }
}
```

Пути к токену различаются: регистрация — `access_token.access_token`,
вход — `token.access_token`.
Выданный токен проверяется запросом к защищённому списку собственных объявлений.

## Создание объявления

`POST /create-listing`, `Authorization: Bearer <token>`.
Тело: **multipart/form-data**.

| Поле | Значение в тестах |
| --- | --- |
| `name` | Тестовая книга по Python |
| `category` | Книги |
| `condition` | Новый |
| `city` | Москва |
| `description` | Тестовое объявление для проверки API учебного сервиса. |
| `price` | 1500 |

В форме доступны категории: Авто, Книги, Садоводство, Хобби, Технологии.
Изображения необязательны; фронтенд добавляет выбранные файлы в поле `images`.
В тестах объявление создаётся без изображения.

В `requests` поля передаются через `files={name: (None, str(value)), ...}`.
Значение `None` исключает имя файла у обычного поля, а использование `files`
формирует multipart-тело. Заголовок `Content-Type` и `boundary` создаёт библиотека.

Успех: **201 Created**, тело — объект объявления:

```json
{
  "id": 456,
  "name": "Тестовая книга по Python",
  "category": "Книги",
  "condition": "Новый",
  "city": "Москва",
  "description": "Тестовое объявление для проверки API учебного сервиса.",
  "price": 1500,
  "owner": 123,
  "updatedAt": "<ISO timestamp>",
  "createdAt": "<ISO timestamp>",
  "img1": null,
  "img2": null,
  "img3": null,
  "isFavorite": null
}
```

В multipart-запросе цена строковая, в ответе — число.

## Чтение собственных объявлений

`GET /profile/listings/1`, `Authorization: Bearer <token>`.
Последний сегмент — номер страницы, а не ID объявления.

Успех: **200 OK**, объект с ключами `offers` и `totalPages`.
`offers` содержит объекты объявлений с их полями, ID и владельцем.
Для нового пользователя и после удаления единственного объявления:

```json
{"offers": [], "totalPages": 0}
```

Этот запрос используется для проверки сохранения, редактирования и удаления.

## Редактирование

`PATCH /update-offer/{id}`, `Authorization: Bearer <token>`.
Тело: **multipart/form-data**, тот же набор из шести полей, что при создании.
В тесте меняется только `name`, остальные значения сохраняются.

Успех владельца: **200 OK**, тело — объект обновлённого объявления с тем же
`id` и `owner`. Изменение дополнительно проверяется через GET.

При отправке только `name` сервер вернул **400** с сообщениями о пустых
`category`, `condition`, `city` и `description`. Поэтому тест отправляет полный
набор полей, как обработчик формы редактирования во фронтенде.

Под токеном второго пользователя: **401 Unauthorized**.

```json
{
  "message": "Оффер не найден или у вас нет прав на его редактирование",
  "error": "Unauthorized",
  "statusCode": 401
}
```

Отрицательный тест отправляет корректное полное тело и меняет только токен
пользователя. После отказа проверяются исходные поля и владелец объявления.

## Удаление

`DELETE /listings/{id}`, `Authorization: Bearer <token>`, без тела запроса.

Успех: **200 OK**.

```json
{"message": "Объявление удалено успешно"}
```

После удаления список собственных объявлений пуст.
Повторный DELETE того же ID при исследовании вернул **500**, поэтому очистка
предварительно проверяет наличие объекта и не повторяет удаление отсутствующего.
Это наблюдение о стенде, не дополнительный сценарий задания.

## Как воспроизвести исследование через Chrome DevTools

1. Открой сайт в Chrome, нажми `F12` и выбери **Network**.
2. Включи **Preserve log**, выбери фильтр **Fetch/XHR**, очисти список запросов.
3. Зарегистрируй тестового пользователя с новым email. Найди `signup`.
4. В **Headers** проверь URL, метод и статус; в **Payload** — JSON;
   в **Response** — пользователя и вложенный токен.
5. Выйди и войди этим пользователем. Аналогично проверь `signin`.
6. Создай объявление, измени название и удали его. Изучи `create-listing`,
   `update-offer/{id}` и `listings/{id}`; у POST/PATCH проверь **Form Data**.
7. Повтори регистрацию с занятым email и проверь ответ `400`.
8. Для запрета редактирования создай второго пользователя. В API-клиенте
   повтори PATCH первого пользователя с токеном второго: ожидается `401`.
   Используй только собственные тестовые аккаунты и объявления.

Для переноса запроса в Postman можно выбрать в Network **Copy → Copy as cURL**,
а затем **Import → Raw text** в Postman. Токены и HAR-файлы не нужны в репозитории.
